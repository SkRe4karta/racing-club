# Racing Club — 2.0.0-alpha.2

Учебная информационная система клуба любителей скачек: учёт владельцев, лошадей и жокеев, планирование заездов и фиксация результатов. Интерфейс на русском языке, светлая и тёмная темы, адаптивная боковая навигация, календарь и печатные стили. Добавлены регистрация OWNER/JOCKEY/VIEWER, вход/выход, проверка статуса, роли ROOT/ADMIN и миграции. Публичный просмотр сохранён; операции записи проверяют права и принадлежность. В Alpha 2 добавлены кабинеты OWNER/JOCKEY, редактирование своих профилей и лошадей, отдельные заявки с двусторонним согласованием и внутренние уведомления. Административный допуск — Alpha 3. Ручная локальная проверка Alpha 2 подтверждена пользователем; коммит и push в текущую feature-ветку разрешены.

Исходный проект: [ZZAY-GIT/cyccle](https://github.com/ZZAY-GIT/cyccle). Разработчики исходной версии — Зелёнкин Д.В., Хилов Д.А., Амплеенков Д.О., группа 241-327, Московский Политех. Лицензия MIT, см. [LICENSE](LICENSE).

Документация Alpha 2: [использование и миграции](docs/ALPHA2.md), [фактические проверки](docs/ALPHA2_VALIDATION.md).

## Возможности

- Кабинеты OWNER/JOCKEY: профиль, свои лошади, история и спортивная статистика, предстоящие соревнования, заявки и уведомления.
- Заявки в отдельной таблице: инициатор выбирает пару, вторая сторона подтверждает или отклоняет; отмена до закрытия регистрации. После обоих согласий требуется решение администратора, переноса в `results` нет.
- Уведомления получателю: список, непрочитанные, просмотр, отметка прочитанного и переход к заявке.

- Главная: реальные счётчики, ближайшие старты, предупреждение о просроченных заявках, последние протоколы, распределение состязаний по состояниям и лидеры по победам.
- Владельцы: поиск по ФИО и телефону, сортировка, карточка и список лошадей.
- Лошади: поиск по кличке и владельцу, пол, возраст, сортировка, карточка и история выступлений.
- Жокеи: поиск по ФИО, сортировка по имени, возрасту и рейтингу, карточка и история. Исходный рейтинг не пересчитывается.
- Будущие состязания: список и месячный календарь, поиск по названию, дате и месту, динамические пары «лошадь — жокей».
- Завершение: время в секундах (`124.50`) или минутах (`02:04.50`), либо дисквалификация; проверка всех строк, атомарное сохранение и автоматические места. Одинаковое время сохраняет исходный алгоритм: `1, 1, 3`.
- Архив: неизменяемые протоколы и создание прошедшего состязания сразу с результатами.
- CSV всех справочников, обоих списков состязаний и отдельных протоколов. UTF-8 с BOM и разделитель `;`, защита от формул в ячейках. Экспортируется весь отфильтрованный список, независимо от страницы.
- По 20 записей на странице, фильтры сохраняются в GET-параметрах. Недопустимая сортировка заменяется штатной; некорректная страница ограничивается доступным диапазоном. Некорректные значения даты, пола и возраста в фильтрах игнорируются.
- Вычисляемые победы, призовые места и процент побед считаются только по завершённым выступлениям, включая дисквалификации в числе выступлений. Без завершённых выступлений процент и последний результат показываются как отсутствие данных.
- Тема хранится в `localStorage`; до первого выбора используется системная. Печать доступна кнопкой вверху или через Ctrl+P, на телефоне — через меню браузера.

## Схема и правила сохранности

Источник истины — `app/models.py`. Сохранены таблицы `owners`, `horses`, `jockeys`, `competitions`, `results`, все поля, типы, связи и ограничения, включая уникальность лошади **и жокея** в одном заезде.

Фактические имена отличаются от некоторых формулировок ТЗ: `nickname`, `gender`, `title`, `event_date`, `event_time`, `finish_time_seconds`. Исходные состояния — **`planned` / `completed`**, а не `finished`. Они сохранены без конвертации данных. Просроченный запланированный старт не становится завершённым автоматически.

Обычный запуск не создаёт и не изменяет схему. Используйте явные миграции: на новой БД `flask --app run db upgrade`; на проверенной копии v1.1 сначала `flask --app run adopt-legacy`, затем `flask --app run db upgrade`. Процедура, резервные копии и ограничения описаны в [docs/ALPHA1.md](docs/ALPHA1.md). `seed.py` отказывается работать с непустой БД и никогда не очищает её. Тесты создают отдельные базы, не используют рабочий `DATABASE_URL`.

## Локальный запуск с SQLite

Нужны Python 3.14 с модулем `venv` и pip. Из корня проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"
export SESSION_COOKIE_SECURE=false  # только локальный HTTP
flask --app run db upgrade  # только для новой БД; для v1.1 см. процедуру выше
flask --app run create-root --email your-email@example.org
python run.py
```

Открыть **http://127.0.0.1:5000**. Если `DATABASE_URL` не задан, используется `instance/races.db`. Существующая локальная база сохраняется. Папка создаётся автоматически.

Для постоянных аккаунтов сохраните один случайный ключ в защищённом окружении и используйте его при всех запусках (не выводите в общий лог). Например для отдельного временного локального окружения:

```bash
export SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"
python run.py
```

Без `SECRET_KEY` приложение отказывается запускаться. Смена ключа завершает прежние сессии. Secure cookies включены по умолчанию; только для локального HTTP задайте `SESSION_COOKIE_SECURE=false`. `.env` автоматически читает **Docker Compose**; при обычном запуске Python переменные нужно экспортировать в окружение самостоятельно.

### Отдельные демонстрационные данные

Используйте отдельную, ранее не заполненную БД; после команды запускайте приложение с тем же `DATABASE_URL`:

```bash
export DATABASE_URL="sqlite:////tmp/racing-demo.db"
flask --app run db upgrade
python seed.py
python run.py
```

Повторное заполнение непустой БД завершается с ненулевым кодом без удаления записей. Не удаляйте рабочую БД ради демонстрации. Даты в демонстрационном наборе фиксированы, поэтому запланированное состязание может отображаться как ожидающее завершения — это штатное поведение.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | URI SQLAlchemy; без значения используется SQLite. PostgreSQL: `postgresql+psycopg://USER:PASSWORD@HOST:5432/DBNAME` |
| `SECRET_KEY` | Постоянный случайный ключ сессии/CSRF, обязателен при обычном запуске и в Compose |
| `SESSION_COOKIE_SECURE` | `true` по умолчанию для HTTPS; явно `false` только для локального HTTP |
| `POSTGRES_USER` | Пользователь PostgreSQL в Compose, по умолчанию `racing` |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL, обязателен в Compose |
| `POSTGRES_DB` | База PostgreSQL, по умолчанию `racing` |
| `WEB_BIND` | Адрес публикации на хосте; по умолчанию `127.0.0.1` |
| `WEB_PORT` | Порт публикации на хосте; по умолчанию `8080` |
| `COMPOSE_PROJECT_NAME` | Имя проекта Compose: отдельные сети и тома для окружений |

Для пароля в Compose удобно использовать URL-безопасную случайную hex-строку. В самостоятельно заданном `DATABASE_URL` специальные символы пароля должны быть URL-кодированы. Реальные секреты храните только в локальном `.env` или переменных окружения, исключённых из Git.

## Docker Compose и PostgreSQL 18

Нужны Docker Engine и **Compose v2**. Из корня проекта:

```bash
cp .env.example .env
```

Для новой локальной БД заполните `SECRET_KEY` и `POSTGRES_PASSWORD` в `.env` своими значениями, а для HTTP задайте `SESSION_COOKIE_SECURE=false`. Для существующей v1.1 сначала выполните резервное копирование и `adopt-legacy` по [инструкции](docs/ALPHA1.md), не используйте установочный сценарий без проверки. Каждое можно сгенерировать командой `python3 -c 'import secrets; print(secrets.token_hex(32))'`. Не публикуйте полученные значения.

```bash
docker compose config --quiet
docker compose build
docker compose up -d db
docker compose run --rm web flask --app run db upgrade
docker compose run --rm web flask --app run create-root --email your-email@example.org
docker compose up -d web
docker compose ps
curl --fail http://127.0.0.1:8080/health
docker compose logs --tail=100 web
```

Адрес: **http://127.0.0.1:8080**. Внутри контейнера Gunicorn слушает `0.0.0.0:8080`, debug выключен; процесс работает от непривилегированного пользователя. Схема обновляется отдельной командой миграции до запуска web; worker не выполняют DDL. Web ожидает `pg_isready` базы. `/health` проверяет реальный SQL-запрос. PostgreSQL не публикует порт наружу.

Постоянный именованный том монтируется в `/var/lib/postgresql`, согласно [официальному описанию PostgreSQL 18](https://hub.docker.com/_/postgres). Изменившийся в PostgreSQL 18 каталог `PGDATA` уже учитывается образом. Это запуск новой БД, а не процедура обновления старого тома PostgreSQL другой основной версии.

Перезапуск сохраняет данные:

```bash
docker compose restart web
```

Остановка проекта также сохраняет постоянный том:

```bash
docker compose down
```

**Не добавляйте `-v` к `down`: это удалит том.** Не меняйте имя проекта или параметры существующей БД без понимания, какой том ей принадлежит. Переменные `POSTGRES_*` задают начальные параметры новой БД; изменение `.env` не меняет пароль и пользователя уже инициализированного тома. Перед обслуживанием рабочей БД используйте отдельную резервную копию.

## TEST, STAGE, PROD

В лабораторной №3 использовались `racing-test`, `racing-stage`, `racing-prod`; браузер основной ОС обращался через `127.0.0.1:8081`, `:8082`, `:8083`. На STAGE/PROD рабочая папка — `/opt/racing-club`. Виртуальные машины при модернизации не изменялись.

Для каждого независимого окружения задавайте своё `COMPOSE_PROJECT_NAME` (`racing-test`, `racing-stage`, `racing-prod`) и собственные секреты. На разных ВМ внутренний опубликованный порт может оставаться `8080`, а внешние `8081/8082/8083` задаются пробросом портов гипервизора. Если проброс обращается к сетевому адресу гостевой ВМ, задайте `WEB_BIND=0.0.0.0` в её контролируемой сети; по умолчанию доступ ограничен loopback. При нескольких проектах на одном хосте задайте различные `WEB_PORT`.

Не копируйте новый `.env` поверх рабочего, не заменяйте старые тома и не запускайте заполнение рабочей БД.

## Автоматическая проверка и подготовка TeamCity

После установки зависимостей:

```bash
python -m pip check
python -m compileall -q app migrations tests run.py seed.py gunicorn.conf.py
python -m unittest tests.review_suite -v  # согласованные 10 тестов
```

Проверки не требуют ручных действий в браузере и используют SQLite **в памяти**, независимо от локальной рабочей БД. Команды возвращают ненулевой код при ошибке. Для установленного Docker/Compose доступны приведённые выше команды проверки конфигурации, сборки и `/health`.

Репозиторий содержит фиксированные зависимости, Dockerfile, healthcheck, шаблон переменных окружения, автоматические функциональные проверки и исключения секретов/БД из Git. Эти команды можно использовать как будущие шаги сборки TeamCity. Сам TeamCity, CI/CD, интеграция с GitHub и следующие лабораторные работы здесь не настроены.

### Исторические проверки версии 1.1

Следующие сведения относятся к прежней модернизации v1.1; результаты alpha.1 фиксируются отдельно в [docs/ALPHA1_VALIDATION.md](docs/ALPHA1_VALIDATION.md). Проверки v1.1 выполнены на Python 3.14.4. Исходные 9 сценариев и 10 новых регрессий проверены на SQLite и отдельном временном PostgreSQL 18. Проверены атомарность, запрет изменения результатов, дисквалификация, одинаковое время, некорректные/несуществующие участники, кириллический поиск, фильтры, сортировка, пагинация, CSV, CSRF, HTML-экранирование, статистика и страницы без данных. Особенность регистра кириллицы в PostgreSQL с локалью C исправлена и проверена отдельно.

Интерфейс просмотрен в реальном Chrome через Playwright: настольный экран 1440 px, планшет 768 px, телефоны 390 и 320 px. Проверены темы, мобильное меню, динамические строки, сохранение темы и отсутствие горизонтального переполнения страницы. Скриншоты проверки создавались отдельно в `/tmp`, вне репозитория.

В среде проверки отсутствует плагин `docker compose`, а Docker daemon недоступен текущему пользователю. YAML разобран и проверены его ключевые параметры; **сборка образа и запуск Compose не выполнялись**. PostgreSQL и Gunicorn проверялись отдельными локальными процессами с временными данными. Для приёмки контейнерного режима выполните команды из раздела Docker на машине с Compose v2.

## Публикация

Создайте собственный репозиторий GitHub и настройте TeamCity отдельно. Перед публикацией проверьте `git status`, не добавляйте `.env`, `instance/`, резервные копии и локальные БД. `origin` исходного репозитория не изменялся, commit/push автоматически не выполнялись.

Возможное название коммита: `Modernize racing club UI, validation and deployment setup`.
