профиль. Заявки, редактирование профиля, административный UI пользователей,
уведомления, прогнозы, аудит и новый дизайн пока не реализованы: см. ROADMAP_V2.md.

Публичная регистрация создаёт **новый** Owner/Jockey и User в одной транзакции.
Рейтинг нового жокея — 0. Передача owner_id/jockey_id/status/rating запрещена.
Старые спортивные профили не присваиваются по ФИО или email. Совпадение ФИО разных
людей допустимо, одному профилю нельзя назначить два аккаунта. Процедура доверенной
привязки исторических профилей и UI управления ролями запланированы позже; в этом
выпуске такие изменения выполняются только доверенным обслуживанием после проверки
личности, не через публичную форму. ADMIN публично не регистрируется.

## Конфигурация

Python 3.14; установка: `python -m pip install -r requirements.txt`.
Нужен один постоянный случайный `SECRET_KEY` в защищённом окружении всех workers.
Без него обычный запуск и CLI отказываются работать. Не выводите его в журнал и
не коммитьте `.env`. Обычный Python не читает `.env` автоматически.

Secure cookies включены по умолчанию, HTTPS обязателен для публичного размещения.
Только при локальной работе через HTTP экспортируйте `SESSION_COOKIE_SECURE=false`.
Сессия закрывается с браузером, подпись cookie ограничена 8 часами. Используются
HttpOnly, SameSite=Lax, strong session protection, CSRF и смена содержимого сессии
при входе/выходе. Текущий статус/роль проверяется через загрузку User на запросе.
Отключённые аккаунты не входят и теряют доступ из существующей сессии. Временная
блокировка по лимиту и отключённый аккаунт — разные механизмы.

## Новая локальная БД

Задайте SECRET_KEY, DATABASE_URL и для локального HTTP SESSION_COOKIE_SECURE.
Используйте заведомо отдельную БД, например SQLite в /tmp. Затем:

```bash
flask --app run db upgrade
flask --app run db current
flask --app run create-root --email your-email@example.org
python run.py
```

ROOT-команда интерактивно дважды запрашивает скрытый пароль (12–128 символов).
Пароль не передаётся аргументом команды и не печатается. Команда не повышает роль
существующего аккаунта и отказывает при занятом email или существующем ROOT,
включая отключённый. Частичный уникальный индекс защищает от параллельного создания
второго ROOT. В исходниках и seed нет известной учётной записи ROOT.

Для прежнего небольшого seed сначала примените миграции, затем явно запустите
`python seed.py` только на отдельной пустой БД. Он не создаёт User. Большой генератор
9 390 записей в этот выпуск не включён.

## Обновление существующей v1.1

Не выполнять на настоящих STAGE/PROD в рамках alpha.1. Ниже процедура для
**изолированной копии** старой БД; доставка в рабочие окружения требует отдельной
приёмки, резервной копии и разрешённого окна обслуживания.

1. Остановить запись в исходную БД и создать резервную копию. SQLite копировать
   штатным backup API при остановленном приложении либо `sqlite3 .backup` с учётом
   WAL; PostgreSQL — `pg_dump -Fc`, отдельно сохранить необходимые роли/настройки.
2. Восстановить в отдельную БД PostgreSQL 18 или отдельный файл SQLite. Сверить
   количество записей, связи и несколько протоколов до изменения схемы.
3. Указать DATABASE_URL копии и постоянный SECRET_KEY. Проверить целевой адрес,
   не печатая пароль подключения. Не запускать seed и не очищать таблицы.
4. Выполнить:

```bash
flask --app run adopt-legacy
flask --app run db current
flask --app run db upgrade
flask --app run db check
flask --app run db current
```

`adopt-legacy` принимает только ровно пять исходных таблиц без Alembic, сравнивает
колонки/типы/nullable, индексы, FK, уникальность и PK с замороженной baseline,
отказывает при расхождении и только затем ставит `0001_v11_baseline`. Команда не
меняет спортивные таблицы или записи. Частично изменённая/нестандартная схема
требует ручного анализа; нельзя обходить отказ слепым `stamp head`.

`db upgrade` добавляет `users` и `auth_throttles` (`0002_auth_foundation`). Старые
записи не меняются; owner_id/jockey_id находятся в новой таблице users. На новой
пустой базе обе ревизии выполняются обычным `db upgrade`. Повторный upgrade —
без изменений. Миграции не выполняются при импорте приложения или запуске workers.

5. Сверить прежние записи/протоколы, проверить публичные страницы, CSV и health.
   Создать первоначальный ROOT интерактивно, проверить вход и доступ к формам.
6. Хранить прежнюю копию отдельно. Автоматические downgrade намеренно запрещены:
   удаление таблиц авторизации потеряет новые аккаунты. Откат — восстановление
   проверенной резервной копии с подходящей версией приложения, после отдельного
   разрешения. Этот выпуск не меняет major-версию рабочего PostgreSQL.

## Docker

Образ содержит приложение и миграции, работает от непривилегированного пользователя.
Для **нового отдельного** Compose-проекта заполните .env по .env.example. Для HTTP
явно задайте SESSION_COOKIE_SECURE=false; для HTTPS оставьте true.

```bash
docker compose config --quiet
docker compose build
docker compose up -d db
docker compose run --rm web flask --app run db upgrade
docker compose run --rm web flask --app run create-root --email your-email@example.org
docker compose up -d web
curl --fail http://127.0.0.1:8080/health
```

Для копии v1.1 перед upgrade выполните `docker compose run --rm web flask --app run
adopt-legacy` по процедуре выше. Не запускайте миграцию одновременно из нескольких
контейнеров. Не используйте `down -v`, не заменяйте рабочий .env или том.

## Лимиты и обслуживание

В конфигурации фабрики: LOGIN_LIMIT=5 на нормализованный email за 900 секунд,
LOGIN_IP_LIMIT=30 на адрес за то же окно, REGISTER_LIMIT=10 на адрес. Считаются
попытки, включая успешные; ответ 429 содержит Retry-After. Истечение окна сбрасывает
счётчик при следующей попытке. Параметры можно переопределить конфигурацией Flask
при развёртывании. IP берётся из REMOTE_ADDR, входящему X-Forwarded-For приложение
не доверяет. За reverse proxy потребуется отдельно настроить и проверить доверенную
инфраструктуру, иначе лимит применяется к адресу proxy.

Счётчики живут в БД и атомарно обновляются UPSERT, общие для workers. Ключи — SHA-256
с областью действия, без исходного email/IP/пароля. Для обслуживания после окончания
окна можно запускать `flask --app run prune-auth-throttles`; удаляются только истёкшие
счётчики, спортивные данные и аккаунты не затрагиваются. При недоступной БД операция
не допускается; публичная ошибка не раскрывает SQL/traceback. SQLAlchemy скрывает
параметры в диагностике.

## Воспроизводимые проверки

```bash
python -m pip check
python -m compileall -q app migrations tests run.py seed.py gunicorn.conf.py
python -m unittest discover -v
python -m unittest verify_acceptance verify_modernization -v
```

Согласованный сокращённый прогон — ровно **10 тестов**, существующие проверки сохранены:

```bash
python -m unittest tests.review_suite -v
```

Полный набор при необходимости:

```bash
python -m unittest tests.test_auth tests.test_migrations tests.test_concurrency verify_acceptance verify_modernization -v
```

По умолчанию отдельные SQLite в памяти; конкурентный тест использует временный
SQLite-файл. Для полного прогона на **заведомо одноразовом** PostgreSQL 18 задайте
`RACING_TEST_POSTGRES_URL` на административную БД временного сервера с CREATEDB.
Каждый тест создаёт случайную `racing_test_<uuid>` БД и удаляет только её. Рабочий
DATABASE_URL не читается тестами. Не направляйте тестовую переменную на рабочий
кластер. У PostgreSQL-тестов есть реальная проверка версии 18, ограничений, запросов,
миграций и сохранения прежних записей. Нужны права на локальный сокет/сетевое
соединение. Никаких тестов на настоящих STAGE/PROD.

Документация используемых механизмов: [Flask-Login](https://flask-login.readthedocs.io/),
[Flask-Migrate](https://flask-migrate.readthedocs.io/),
[PostgreSQL 18 ON CONFLICT](https://www.postgresql.org/docs/18/sql-insert.html).
