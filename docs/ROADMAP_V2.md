# Racing Club 2.0 — техническое задание и дорожная карта

## Цель, архитектура и границы
Модернизировать v1.1 в систему управления конным спортивным клубом, сохраняя
Flask, пять исходных спортивных таблиц, данные, публичные URL, поиск, фильтры,
пагинацию, CSV, календарь, результаты и спортивную статистику. Python 3.14,
Flask 3.1, SQLAlchemy 2, PostgreSQL 18, Jinja2, Gunicorn, Docker Compose,
TeamCity; SQLite допускается для изолированных локальных сценариев.
Blueprints отвечают за HTTP, сервисы — за бизнес-транзакции, ORM — за связи и
ограничения; миграции Alembic — единственный путь изменения рабочей схемы.
Не переходить на Django/FastAPI/React/Next.js. Допустимы HTMX и Chart.js.

Это ТЗ конечной системы, а не заявление о готовности всех функций. Реализация
alpha.1 ограничена фундаментом, авторизацией, политикой доступа и миграциями.

## Роли и матрица доступа
| Роль | Разрешённые действия |
| --- | --- |
| ROOT | Все разрешения остальных ролей; пользователи, роли, профили, владельцы, жокеи, лошади, соревнования, заявки, результаты и системные настройки |
| ADMIN | Создание/редактирование соревнований, допуск, заявки, стартовые списки, результаты, дисквалификации, завершение и статистика; без системных настроек ROOT |
| OWNER | Кабинет, собственный профиль, регистрация собственных лошадей, статистика, история лошадей, календарь, заявки с выбором жокея, подтверждения, уведомления |
| JOCKEY | Кабинет, собственный профиль, история выступлений, личный рейтинг и статистика, календарь, заявки с выбором лошади, подтверждение участия, уведомления |
| VIEWER | Зарегистрированный зритель: собственный аккаунт, бесплатные прогнозы, их история/точность, уведомления |
| GUEST | Только чтение публичных владельцев, лошадей, жокеев, соревнований, результатов и рейтингов |

ROOT создаётся доверенной CLI-процедурой. Публично регистрируются только OWNER,
JOCKEY и VIEWER. Привилегированные роли не назначаются через публичный ввод.
Каждое действие проверяет активность пользователя, разрешение и принадлежность
объекта. OWNER не может подставить чужого владельца, JOCKEY — чужой профиль.
Публичная регистрация не присваивает исторические профили по ID/email/ФИО:
создаётся отдельный профиль. Доверенное связывание после проверки личности ROOT
проектируется отдельно; совпадение ФИО само по себе не доказывает личность.

## Предметная модель конечной системы
- User: нормализованный уникальный email, хеш, роль, статус, регистрация и последний
  вход, безопасная сессия. Связи Owner/Jockey один к одному, без дублирования привязки.
- Owner, Horse, Jockey: прежние данные и история; лошадь принадлежит владельцу,
  рейтинг пересчитывается только явно согласованным спортивным алгоритмом.
- Competition: дата, время, место, состояние, правила допуска и сроки заявок.
  Текущие planned/completed сохраняются; расширение жизненного цикла — миграцией.
- Application: соревнование, лошадь, жокей, инициатор, подтверждение каждой стороны,
  решение администратора и временные отметки. Запрещены повторные лошади/жокеи в
  одном старте; изменение пары сбрасывает подтверждения; отказы фиксируются.
- Result: утверждённая пара, время либо дисквалификация, место; завершение атомарно,
  завершённый протокол защищён от случайного изменения; корректировки аудируются.
- Prediction: автор, соревнование, тип победитель/первая тройка, выбор, время,
  результат проверки точности. Уникальность прогноза пользователя по типу/старту.
- Notification: получатель, событие, прочтение, время; выдача только получателю.
- AuditLog: субъект, действие, объект, время и безопасные метаданные без секретов.

## Сценарии и приёмка конечных функций
Регистрация, вход/выход, проверка статуса, восстановление доступа и управление
собственным аккаунтом должны иметь валидацию, CSRF и ограничение запросов.
Кабинеты OWNER/JOCKEY показывают профиль, собственные объекты, историю, календарь,
заявки и уведомления. Подача заявки доступна только с разрешённой лошадью/жокеем;
пара становится допущенной после обеих сторон и администратора. Стартовый список
строится только по допущенным парам. ADMIN создаёт и редактирует соревнования,
проверяет заявки, вносит результаты/дисквалификации, завершает старт. ROOT управляет
пользователями, ролями, всеми предметными объектами и настройками.

Рейтинги, аналитика и графики отражают проверяемые результаты; фильтры по периоду,
участнику и соревнованию согласованы с таблицами и CSV. История доступна из профилей.
Поиск поддерживает кириллицу; пагинация и экспорт сохраняют фильтры. Календарь
показывает реальные даты и состояния, просрочка не завершает состязание автоматически.

Прогнозы исключительно информационные и спортивные, бесплатные: победитель и
упорядоченная первая тройка. Приём закрывается до фактического начала старта;
неучастники, дубли и поздние изменения отклоняются. После утверждения результатов
точность вычисляется воспроизводимо, отменённые старты исключаются из метрики.
Денежные ставки, коэффициенты, призы, кошельки и финансовые операции отсутствуют.

## Интерфейс и нефункциональные требования
Премиальный спортивный стиль: чёрный, графитовый, белый, неоново-зелёный; крупная
типографика, легально используемые фотографии конного спорта, современная сетка,
карточки, графики, умеренные анимации. Публичный сайт — горизонтальная навигация,
кабинеты — боковое меню и панели. Редизайн выполняется в alpha.4. До него текущие
адаптивные страницы сохраняются. Доступность: клавиатура, focus, labels, контраст,
reduced-motion, мобильные экраны и понятные ошибки. Jinja экранирует ввод.

Секреты только в окружении, пароли только хешами; постоянный ключ сессии, HTTPS,
HttpOnly/Secure/SameSite, CSRF на изменяющих запросах, проверка аккаунта при каждом
запросе, общие сообщения об ошибках входа. Ограничитель запросов должен работать
между несколькими worker. Логи не содержат паролей/токенов. Права проверяются на
сервере при прямом HTTP-доступе. Healthcheck выполняет SQL. Индексы и eager loading
обеспечивают предсказуемую работу списков. Схема и старые данные сохраняются.

Данные разнообразные, реалистичные и согласованные по датам, возрастам, владельцам,

## Лабораторные №5–8 и эксплуатация
ЛР №5: GitFlow feature → dev → release/STAGE → стабильный PROD по принятому
процессу. TeamCity получает исходники из origin, проверяет зависимости/синтаксис/
тесты, собирает образ, помечает SHA и версией, публикует в Docker Hub, доставляет
на STAGE с healthcheck и smoke-проверкой. Секреты находятся в защищённых параметрах.
Фиксируются SHA, тег образа, номер сборки и результаты. PROD требует явного допуска;
legacy не используется как цель push. Alpha.1 не меняет настоящие STAGE/PROD.

ЛР №6: согласованные анализаторы Python/security/dependencies, воспроизводимые
правила и отчёты, объективная обработка найденных проблем, содержательные тесты
с изолированными SQLite и PostgreSQL 18. Статические проверки не заменяют HTTP-
и интеграционные проверки. Не отключать защиты ради прохождения набора.

ЛР №7: изменение схемы с versioned Alembic и эквивалентным ручным SQL-планом,
предусловиями, оценкой блокировок/индексов, проверкой данных и временем обслуживания.
Проверить initial install и upgrade с предыдущего релиза на копии; downgrade
с удалением новых данных не считать безопасным rollback. Нужны backup/restore
и совместимая версия приложения; разрушительные откаты запрещены по умолчанию.

ЛР №8: `pg_dump`/`pg_restore`, отдельное хранение и контроль доступа, сроки хранения,
проверка восстановления на изолированном PostgreSQL 18 и измерение RPO/RTO.
Перед PROD — backup, проверенный upgrade, health/smoke, план восстановления,
приёмка и документированный стабильный релиз. Запрет на очистку рабочих БД,
замену томов и неконтролируемое обновление major-версии PostgreSQL.

## Общая готовность
Каждый этап завершается проверенным diff, содержательными коммитами, разрешённым
push feature-ветки и отчётом с реальными командами, результатами/пропусками и
ограничениями среды. Alpha.1 не создаёт PR, не делает merge, не публикует релиз
и не начинает alpha.2. Следующие функции остаются требованиями этого документа.
