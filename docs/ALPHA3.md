# Racing Club 2.0.0-alpha.3 — эксплуатация

Реализовано локально в `feature/v2-alpha-1-foundation` поверх принятого Alpha 2
`2e8b709f807776ab556a87f476dd14bafdf47e38`. Пользователь подтвердил локальную ручную
проверку и разрешил commit/push только в эту feature-ветку. Это не production-релиз;
PR/merge и deployment не выполняются.
Фактические команды и результаты: [ALPHA3_VALIDATION.md](ALPHA3_VALIDATION.md).

## Роли и точки входа

| Роль | Возможности |
| --- | --- |
| GUEST | Публичные каталоги, календарь, официальный стартовый список, протоколы, CSV, статистика |
| VIEWER | Те же страницы, свой аккаунт и уведомления |
| OWNER | Свой профиль, лошади, заявки, личное согласие владельца, история, уведомления |
| JOCKEY | Свой профиль, заявки, личное согласие жокея, история, уведомления |
| ADMIN | `/admin/`: соревнования, заявки, допуск, результаты, свои действия в журнале |
| ROOT | `/root/`: аккаунты, роли, статусы, доверенные привязки; все функции ADMIN, полный аудит и отдельные административные исключения |

После входа на `/auth/account` доступны ссылки на разрешённые панели; те же ссылки
есть в меню. Защита действует на сервере для каждого GET/POST, независимо от кнопок.
Все изменения — POST с CSRF. Активность и роль аккаунта проверяются заново.
Приватные ответы имеют `Cache-Control: no-store`. Выход — только POST.

## ADMIN: соревнования и заявки

`/admin/` показывает количество запланированных/завершённых соревнований, ожидающих
решения заявок и официальных участников будущих стартов, ближайшие старты и последние
доступные административные действия. Число будущих участников включает сохранённые
исторические стартовые списки; ожидающие заявки в него не входят.

`/admin/competitions` — список с фильтром planned/completed и пагинацией.
`/admin/competitions/new` (также прежний `/competitions/future/add`) создаёт
соревнование **без участников**. Обязательны название, место, будущие дата/время,
дистанция 100–100000 м и лимит 1–1000 участников. Необязательный срок регистрации
должен находиться в будущем и не позже начала. Ввод времени — Europe/Moscow,
срок хранится в UTC. Без срока регистрация закрывается при начале соревнования.

`/admin/competitions/<id>` — административная карточка: условия, заявки,
единственный официальный стартовый список, ввод результатов и публичный протокол.
`/edit` позволяет менять параметры только до начала и при отсутствии действующих
заявок/участников. Ограничение намеренно строже запрета изменения после допуска:
уже отправленное приглашение также относится к конкретным условиям соревнования.
Завершённый старт и прежние участники защищены от изменения параметров.

`/admin/applications` — таблица заявок с номером, соревнованием, парой,
владельцем, реальным инициатором, личными согласиями, датой UTC, статусом и действиями.
Фильтры: соревнование и статус; пагинация по 20. ADMIN вправе просматривать все заявки.
Подделка роли, пары, служебного статуса и неизвестные поля POST отклоняются.

## Личные согласия и допуск

1. OWNER выбирает свою лошадь и жокея с активным связанным аккаунтом. Отправка
   записывает личное согласие OWNER и `awaiting_jockey`.
2. JOCKEY подтверждает приглашение отдельным POST. Обратный сценарий начинается
   от JOCKEY и требует согласия владельца (`awaiting_owner`).
3. Два личных согласия дают `pending_admin`. Это ещё **не участник**.
4. ADMIN утверждает заявку до начала запланированного соревнования. Срок приёма
   к этому моменту может истечь: решение допускается после регистрации, до старта.
5. В одной транзакции появляются `admin_confirmed`, один Result со ссылкой на заявку,
   уникальный стартовый номер, событие заявки, аудит и уведомления обеим сторонам.
   Другие уже допущенные участники получают уведомление об изменении списка.

При допуске повторно проверяются оба действующих профиля/аккаунта, неизменность
привязок, настоящие исполнители личных согласий в истории, отсутствие лошади/жокея
в Result и свободное место в лимите. Активные заявки дополнительно защищены
частичными уникальными индексами Alpha 2. Повторный допуск возвращает конфликт
без новых строк, событий и сообщений. Ошибка любой записи откатывает всё.

ADMIN может отклонить ещё не допущенную заявку, указав причину 5–500 символов.
Причина целиком сохраняется в аудите; уведомления содержат её краткий текст.
Отказанные/отменённые заявки не создают Result, не считаются выступлениями и
освобождают свои места среди активных заявок. Допущенная заявка не отменяется
обычной кнопкой участника или ROOT: опубликованный стартовый список защищён.
Смена пары всегда требует новой заявки и новых согласий.

ROOT **не может** создавать заявку или подтверждать согласие за спортивную сторону.
Для отмены ошибочного приглашения есть отдельная операция `root-cancel` с причиной,
настоящим actor_id и аудитом; она не меняет timestamps личных согласий.
Старые события ROOT из Alpha 2 сохраняются, но не доказывают личное согласие:
интерфейс не показывает их полученным персональным согласием, допуск отказывает.
Такую заявку нужно явно отменить и заново подать от настоящего спортивного аккаунта.

## Официальный стартовый список и исторические данные

`results` — единственный источник официальных участников; параллельной таблицы
участников нет. `results.application_id` уникален и nullable; `start_number` уникален
в соревновании. Для новых допусков оба значения заполнены. Публичная карточка
показывает номер, лошадь, владельца, жокея, основание допуска и ссылки на профили.
Ожидающие заявки доступны сторонам отдельно в личном кабинете.

Прежние Result v1.1 и Alpha 1 остаются без ссылки и номера. Они обозначены
историческими участниками, без изменения старых протоколов и перенумерации.
Nullable дистанция/лимит у старых Competition означают отсутствие прежних условий,
а не потерю записи. Просмотр, завершение старого запланированного списка, поиск,
календарь, CSV и статистика сохранены.

Прямое создание состязания с парами и готового прошлого протокола закрыто.
POST `/competitions/past/add` возвращает 410; GET объясняет новую процедуру.
Прежние сервисные точки записи также не позволяют обойти допуск.

Исключение `/admin/competitions/<id>/manual` доступно только ROOT: ручной допуск
с обязательной причиной. Проверяются начало/статус, существование профилей,
блокировка связанных аккаунтов, активные конфликтующие заявки, лошадь/жокей и лимит.
Историческая пара без аккаунтов допустима только этим явно обозначенным исключением.
Создаются Result, номер, аудит с причиной и уведомления связанным участникам.
Личные согласия и фиктивная Application не создаются. В интерфейсе основание —
«Исключение ROOT». У ADMIN доступа к этому механизму нет.

## Результаты, завершение и коррекция

`/competitions/complete/<id>` принимает результаты только после запланированного
начала и только для полного официального списка. Для каждой строки нужен ровно
один исход: положительное конечное время (секунды либо MM:SS.ss), DSQ или DNF.
Пустой/неполный протокол, чужие ID, NaN/Infinity и противоречивые исходы отклоняются.
DSQ и DNF не имеют времени и места. Нулевой список завершить нельзя. Даже если все
участники имеют DSQ/DNF, это определённый спортивный протокол, без призовых мест.

Места считаются по времени с точностью до сотых: одинаковое время делит место,
например `1, 1, 3`. Весь протокол, `completed`, аудит и уведомления публикуются
атомарно. Два одновременных запроса не могут завершить один старт дважды.
Завершённое соревнование автоматически попадает в архив; повторное открытие
страницы не записывает результаты и не меняет статистику.

После завершения обычные действия не меняют результаты, пару, номера и условия.
ROOT может открыть `/admin/competitions/<id>/correct`, указать причину и представить
**весь** исправленный протокол. Скрытый revision защищает от устаревшей формы,
причина обязательна, отсутствие изменений отклоняется. Участники и номера остаются
прежними; места заново рассчитываются. Аудит сохраняет полный старый и новый снимок
каждой строки с ID, парой, временем, исходом и местом. Исходная публикация и все
промежуточные корректировки остаются в неизменяемом журнале; Result не удаляются.
Связанные аккаунты получают уведомление о коррекции.

Статистика строится из Result завершённых соревнований: выступления, победы,
вторые/третьи места, DSQ, DNF, процент побед, история лошади/жокея и владельца.
Предварительные участники и заявки исключены из завершённых выступлений.
DSQ/DNF входят в число выступлений, но не в победы. Рейтинг v1.1 не пересчитывается;
новая модель рейтинга и графики не добавлялись.

## ROOT: пользователи и доверенные привязки

`/root/users` поддерживает поиск по email, фильтры роли/статуса и пагинацию.
Карточка показывает регистрацию, последний вход и связанные спортивные профили.
ROOT может отключить/восстановить аккаунт, назначить ADMIN из VIEWER и вернуть
ADMIN в VIEWER. Причина обязательна, старая/новая роль и статус сохраняются в аудите.
Блокировка/восстановление отправляет одно уведомление. Повтор без изменений
отклоняется; отключение отзывает сессию при следующем запросе.

ROOT защищён от отключения и смены роли через эти формы. Назначение ещё одного
ROOT запрещено сервисом и уникальным индексом БД. ROOT создаётся только доверенной
CLI-командой `create-root` Alpha 1. Публичная регистрация не создаёт ADMIN/ROOT.
Аккаунты OWNER/JOCKEY нельзя переключить в несовместимую роль: привязки и история
не отрываются. Переход из VIEWER в спортивную роль возможен только через доверенную
привязку свободного исторического профиля. Самостоятельного захвата профиля нет.

`/root/users/<id>/link`: ROOT сначала проверяет принадлежность вне системы,
подтверждает это флажком и указывает безопасное основание проверки. Совпадение ФИО
недостаточно. Только активный VIEWER без профилей может получить свободный Owner
или Jockey и соответствующую роль. Существующий спортивный аккаунт не перепривязывается;
профиль, принадлежащий другому User, недоступен. FK/UNIQUE, блокировки и условный
UPDATE защищают от конкурентной привязки. Лошади и история старого профиля сохраняются.
Документы, пароли и секреты в основание проверки не вводятся.

Из системной панели также доступны прежние защищённые формы владельцев, жокеев,
лошадей и профилей. Удаление спортивной истории и произвольный редактор БД не предоставляются.

## Аудит и уведомления

`/admin/audit`: ADMIN видит только записи со своим actor_id, ROOT — все записи.
У обычных аккаунтов и гостей доступа нет. Журнал показывает время UTC, действие,
тип/ID объекта, actor_id, причину и старые/новые значения. У журнала нет изменяющих
маршрутов; триггеры SQLite/PostgreSQL отвергают UPDATE/DELETE.

События: создание/изменение соревнования, утверждение/отказ, вмешательство ROOT,
ручной участник, завершение/коррекция, статус/роль аккаунта и доверенная привязка.
Метаданные формируются явными списками полей, никогда из полной формы или User.
Хеши, пароли, CSRF, cookie и URI БД не входят в снимки. Причины с явными признаками
секретов/строк подключения отклоняются; оператор также обязан не вводить секреты
в произвольный текст причины. Журнал доступен доверенным администраторам, а не публике.

Уведомления используют прежний личный inbox `/cabinet/notifications`. Их источник —
либо уникальное событие заявки, либо запись аудита; в обоих случаях получатель
уникален для события. Есть переход к заявке или публичному протоколу/списку.
Счётчики, пагинация и защищённая идемпотентная отметка прочитанного сохранены.
Внешняя почта не нужна. Изменение, событие, аудит и уведомления входят в одну транзакцию.

## Миграция и обновление

Новая ревизия `0004_administration` после неизменённых `0001`, `0002`, `0003`:

- `competitions.distance`, `max_participants` nullable с CHECK диапазонов;
  `revision` NOT NULL с нулевым default для прежних записей;
- `results.application_id` FK RESTRICT + UNIQUE; nullable `start_number` с CHECK
  положительности и UNIQUE внутри старта; `did_not_finish` NOT NULL default false
  и CHECK несовместимости с DSQ;
- `audit_logs`: актор FK RESTRICT, действие, объект, время, причина, JSON-снимки,
  индексы по актору/объекту и триггеры неизменяемости;
- у `notifications` nullable application/event, новые audit/competition FK RESTRICT,
  UNIQUE получателя/аудита и CHECK обязательного согласованного источника.

Старые поля/данные не переписываются. На SQLite Alembic пересоздаёт только
`results` и `notifications` для добавления ограничений, копируя все прежние поля;
записи и FK сохраняются. PostgreSQL применяет транзакционный ALTER. Никакого
TRUNCATE/очистки, удаления спортивных данных или изменения опубликованных ревизий нет.
Разрушительный downgrade запрещён.

Для **новой отдельной** БД задайте постоянный SECRET_KEY и явный DATABASE_URL:

```bash
.venv/bin/flask --app run db upgrade
.venv/bin/flask --app run db current
.venv/bin/flask --app run db check
.venv/bin/flask --app run create-root --email your-email@example.org
```

Для обновления Alpha 2 сначала сохраните и проверьте backup, восстановите копию
в изолированном окружении и отрепетируйте `db upgrade`/`db check`, сверив записи,
FK и протоколы. На SQLite остановите запись на время изменения схемы. На PostgreSQL
учтите блокировки ALTER и запускайте миграцию один раз до workers. Фабрика и
Gunicorn не выполняют миграции. Рабочие TEST/STAGE/PROD в этом этапе не менялись.
Откат требует проверенной резервной копии и совместимого приложения, не удаления таблиц.

Все операции старта блокируют сначала Competition; изменения аккаунтов блокируют
свои User. Перед чтением стартового списка условный UPDATE revision резервирует
операцию, включая SQLite. PostgreSQL использует SELECT FOR UPDATE; общая строка
соревнования сериализует разных администраторов, даже для разных заявок одного старта.
Аккаунты дополнительно используют условный UPDATE прежней роли/статуса.
Ошибки и устаревшие операции завершаются rollback с понятным ответом.

## Локальная ручная проверка

Отдельный временный набор и адрес приведены в ALPHA3_VALIDATION.md. Пароли случайные,
`accounts.txt`/`config.json` имеют права 600, каталог 700, всё вне Git.
HTTP слушает только `127.0.0.1`; Secure-cookie выключена только в этом процессе.
Есть свободные пары/старты, приглашения обеих сторон, pending_admin, допущенные
пары, готовое к завершению соревнование, архивные результаты и административная история.

Для собственного полного сценария создайте старт с датой сегодня и временем
на несколько минут позже текущего московского: успейте согласовать и допустить пару
до начала. После этого времени результаты можно опубликовать без изменения часов
или обхода правил. Для немедленной проверки завершения есть отдельный уже начавшийся
старт «Готово к завершению — внесите результаты сейчас».

Порядок: ROOT → аккаунты/статусы → ADMIN создаёт пустой старт → OWNER подаёт заявку →
JOCKEY подтверждает → ADMIN допускает → публичный список → повторный допуск →
после начала полный протокол → архив/профили/статистика → уведомления → аудит →
проверка 403 для OWNER → мобильный экран. Основные формы работают без JavaScript.

Пользователь сообщил: «Проверил Alpha 3, разрешаю коммит и push». Ручная проверка
подтверждена, commit/push только в текущую feature-ветку разрешены. Отдельные
выполненные им сценарии не перечислены; автоматические проверки не приписываются
пользователю. Сервер оставляется работающим. При дефектах — исправление и повтор
нужных проверок.
Alpha 4, прогнозы, графики, большой генератор, TeamCity и deployment не выполнялись.
HTTPS Caddy/443 остаётся обязательным для финального 2.0.0; сейчас не развёртывается.
