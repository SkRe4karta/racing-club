## Изоляция и проверенные сценарии

SQLite-тесты используют отдельные БД в памяти; конкурентный сценарий — временный
SQLite-файл. Тестовая переменная PostgreSQL явно удалена из окружения SQLite-прогона.
Рабочий `DATABASE_URL` не используется: конфигурация тестов задаёт собственные URI.

Для PostgreSQL создан **новый** кластер в приватном временном каталоге `/tmp`,
инициализированный `initdb` PostgreSQL 18.6. TCP выключен (`-h ""`), подключения
разрешены только через Unix-сокет внутри этого каталога, host-аутентификация
запрещена. Каждый тест создаёт случайную `racing_test_<uuid>` БД и удаляет только
её. После прогона SQL-проверка подтвердила версию 18.6 и отсутствие оставшихся
`racing_test_*` БД (0); затем временный кластер остановлен. Приведённый адрес — свидетельство
выполненного прогона, а не постоянная конфигурация приложения. Рабочие SQLite,
STAGE/PROD и существующие Docker-тома не использовались.

Полный набор проверяет:

- регистрацию OWNER/JOCKEY/VIEWER, нормализацию и уникальность email, хеши scrypt,
  ошибки регистрации и запрет повышения привилегий или присвоения чужого профиля;
- вход/выход, неверный пароль, последний вход, отключение аккаунта, смену роли,
  срок сессии, поддельную cookie, изменение User-Agent и безопасное перенаправление;
- публичный просмотр GUEST, запрет прямых HTTP-запросов записи для GUEST/VIEWER,
  границы OWNER/JOCKEY/ADMIN/ROOT и проверку принадлежности объектов;
- CSRF: отсутствующий, поддельный, чужой, просроченный токен и ротацию при входе;
- CLI создания ROOT: скрытый пароль, слабый пароль, занятый email и запрет повторного
  ROOT, а также ограничения ролей/профилей и уникальности на уровне самой БД;
- лимиты по email/IP, игнорирование поддельного X-Forwarded-For, истечение окна,
  очистку истёкших счётчиков; 16 параллельных запросов через два приложения,
  из которых допущены ровно 5;
- фабрику без автоматического DDL, чистую установку миграций, adopt/upgrade v1.1,
  сохранение всех полей записей пяти старых таблиц и уникальности участников,
  отказ при несовместимой схеме и разрушительном downgrade, повторный upgrade,
  PostgreSQL offline SQL и совпадение схемы с моделями (`db check`);
- старые 19 регрессий: страницы и пустые состояния, поиск кириллицей, фильтры,
  сортировку, пагинацию, CSV, календарь, историю, статистику, результаты,
  дисквалификации, одинаковое время, валидацию и атомарность сохранения;
- безопасный ответ при недоступной БД, экранирование HTML и защиту CSV от формул.

CSRF в тестах авторизации включён; существующая изолированная настройка прежних
регрессий не менялась. Успех этих проверок не является измерением покрытия:
требование ЛР №7 о покрытии не менее 40% функциональности остаётся будущей приёмкой.

## Готовность Docker и ограничения среды

Фактически выполнены `docker version` и `docker compose version`. Docker CLI
29.1.3 установлен, но соединение с `/var/run/docker.sock` получает `permission denied`,
в том числе при проверке вне sandbox. Плагин Compose отсутствует:
`docker: unknown command: docker compose`.

**Сборка образа, запуск Compose и контейнерный healthcheck в этой проверке не
выполнялись.** Системные права, группы и Docker socket не менялись; Docker/Compose
не устанавливались. Контейнерная готовность требует проверки на доступном
Docker-хосте по инструкции `docs/ALPHA1.md`.

Отдельно реально выполнена статическая проверка Dockerfile и Compose: YAML разобран
через PyYAML; подтверждены Python 3.14, включение migrations в образ, непривилегированный
пользователь, порт приложения 8080, PostgreSQL 18 без опубликованного порта,
постоянный том, ожидание готовности БД и передача SESSION_COOKIE_SECURE. Это
проверка конфигурационных файлов, а не подтверждение контейнерной сборки.
Gunicorn и браузер в рамках этого заключительного задания повторно не запускались.
