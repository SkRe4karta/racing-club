Автоматические проверки выполнены. Пользователь подтвердил локальную ручную

## Кабинеты и собственные объекты

После входа откройте «Личный кабинет» в меню или на странице аккаунта.
`/cabinet/` показывает профиль, статистику, историю выступлений, предстоящие
участия из прежних стартовых списков, соревнования с открытой регистрацией,
активные заявки, историю завершённых заявок и последние уведомления.
OWNER также видит число собственных лошадей и ссылки на их карточки/редактирование.
Статистика использует только завершённые результаты; дисквалификации учитываются
в числе выступлений, но не в победах или призовых местах. Исходный рейтинг жокея
сохраняется, алгоритм его пересчёта не добавлялся.

Профиль редактируется через `/cabinet/profile/owner/<id>/edit` или
`/cabinet/profile/jockey/<id>/edit`. OWNER меняет свои ФИО, адрес, телефон;
JOCKEY — свои ФИО, адрес и возраст. Роль, статус, email, привязки аккаунтов и рейтинг
не принимаются этими формами. ROOT может редактировать любой спортивный профиль;
ссылки доступны в публичных карточках при наличии прав. ADMIN таких прав не получает.
Публичные карточки и существующие сведения в них остаются публичными, как в Alpha 1;
личные заявки, события и уведомления через них не раскрываются.

`/horses/add` сохраняет прежний маршрут создания. OWNER может указать только себя
в качестве владельца; значение заранее выбрано в форме. `/horses/<id>/edit`
проверяет владение на сервере. Меняются кличка, пол и возраст; смена владельца через
эту форму запрещена, в том числе ROOT, чтобы не менять стороны действующих заявок.
Карточка сохраняет спортивную историю и показывает собственнику приватные заявки.
Физическое удаление лошадей не предоставляется; DELETE не поддерживается.
Новые внешние ключи `RESTRICT` также защищают связанные заявки и журнал.

## Создание и согласование заявки

1. OWNER открывает будущее соревнование, нажимает «Заявить на соревнование»,
   выбирает свою лошадь и жокея с активным связанным аккаунтом.
2. После отправки заявка получает `awaiting_jockey`. Согласие OWNER уже записано.
3. JOCKEY открывает приглашение через кабинет, заявки или уведомления, подтверждает
   либо отклоняет его отдельным POST.
4. При подтверждении записывается второе согласие и состояние `pending_admin`.
   Обе стороны получают уведомление о подтверждении и ожидании администратора.

Обратное направление: JOCKEY выбирает лошадь, свой профиль сервер определяет сам.
Создаётся `awaiting_owner`; подтверждение или отказ делает её владелец.
Исторический профиль без активного связанного аккаунта не участвует в этом
сценарии: автоматически присваивать профиль или считать его согласие полученным
нельзя. Обе стороны должны иметь активные аккаунты также в момент подтверждения.
Отказ и отмена остаются доступны, если второй аккаунт впоследствии отключён.

ROOT может подать заявку от выбранной стороны (это явно указано в форме),
подтвердить или отклонить чужую заявку и отменить её. Действия фиксируются с реальным
ID ROOT. Инициатор, включая ROOT, не подтверждает собственную заявку вместо второй
стороны. Уведомления доступны только их получателю, включая ROOT.

## Состояния и сроки

| Состояние | Значение |
| --- | --- |
| `awaiting_owner` | Согласие жокея есть; ожидается владелец |
| `awaiting_jockey` | Согласие владельца есть; ожидается жокей |
| `pending_admin` | Оба согласия есть; ожидается решение администратора |
| `admin_confirmed` | Зарезервировано для Alpha 3; операции установки в Alpha 2 нет |
| `rejected` | Приглашение отклонено второй стороной; терминальное состояние |
| `cancelled` | Заявка отменена инициатором или ROOT; терминальное состояние |

Согласование обеими сторонами и ожидание администратора представлены одним
согласованным состоянием, без промежуточной противоречивой записи. Alpha 2 не
создаёт `Result` из заявки и не показывает её окончательно допущенным участником.
Прежние участники из Alpha 1 и их протоколы сохраняются отдельно.

Пара неизменяема. Для её изменения инициатор отменяет заявку и создаёт новую:
согласия и история прежней пары не переносятся. Отклонённую/отменённую заявку нельзя
подтвердить повторно. Повторное решение возвращает понятный конфликт без повторных
уведомлений. История решений доступна в карточке заявки.

Приём, подтверждение, отказ и отмена разрешены только до срока регистрации и до
начала запланированного соревнования. Поле `competitions.registration_deadline`
необязательно. ADMIN/ROOT могут указать его при создании соревнования через
существующую форму; срок позже начала запрещён. Ввод — `Europe/Moscow`, хранение —
UTC. Без явного срока регистрация закрывается в момент начала по времени клуба.
Завершённое или уже начавшееся соревнование не принимает новые заявки.

На один заезд разрешена только одна активная заявка каждой лошади и каждого жокея.
Уникальные частичные индексы обеспечивают это в PostgreSQL и SQLite. Прежние пары
в `results` также проверяются перед созданием заявки. На PostgreSQL изменения
блокируют сначала соревнование, затем заявку; в SQLite повторные решения защищены
условным UPDATE по прежнему состоянию. Ошибка сохранения уведомления откатывает и
саму заявку/решение. Событие, изменение заявки и уведомления — одна транзакция.

## Уведомления и интерфейс

`/cabinet/notifications` — личный список с количеством непрочитанных и пагинацией
по 20 записей. `/cabinet/notifications/<id>` — просмотр с переходом к заявке.
Просмотр GET не меняет состояние; отметка прочитанного — защищённый POST, повторная
отметка не меняет дату. Чужие ID возвращают 404.

Все изменяющие формы защищены CSRF. Основные действия работают без JavaScript;
при наличии JavaScript кнопка отправки блокируется на время запроса. Списки заявок
имеют фильтр по состоянию и пагинацию. Таблицы прокручиваются внутри своего блока
на телефоне. Сохранены тема, клавиатурная навигация, печать и reduced-motion.

## Схема, установка и обновление

Миграция `0003_applications` следует за `0002_auth_foundation` и добавляет:

- `applications`: соревнование, пара, аккаунты сторон, инициатор/сторона, состояние,
  согласия и временные отметки; CHECK, FK RESTRICT и частичные уникальные индексы;
- `application_events`: последовательная история создания/подтверждения/отказа/отмены;
- `notifications`: получатель, заявка, событие, текст, создание и прочтение;
  уникальность `(user_id, event_id)` и индекс личного непрочитанного списка;
- nullable `competitions.registration_deadline` без изменения прежних строк.

Миграция не импортирует текущие ORM-модели. Пять старых спортивных таблиц,
аккаунты, хеши паролей, привязки и счётчики попыток сохраняются. Автоматический DDL
при запуске отсутствует; разрушительный downgrade запрещён.

На отдельной пустой БД с явно заданными `DATABASE_URL` и `SECRET_KEY`:

```bash
.venv/bin/flask --app run db upgrade
.venv/bin/flask --app run db check
.venv/bin/flask --app run create-root --email your-email@example.org
```

Для обновления Alpha 1 сначала создайте и проверьте резервную копию, отрепетируйте
обновление на изолированной копии и выполните те же `db upgrade` / `db check`
явной отдельной операцией до запуска workers. `adopt-legacy` нужен только для
неуправляемой схемы v1.1 (см. ALPHA1.md). На STAGE/PROD операции в этом этапе не
выполнялись. Откат новых данных требует проверенного backup и совместимой версии
приложения; удаление новых таблиц не является безопасным откатом.

Локальная демонстрация для подтверждённой ручной проверки использует отдельный каталог
`/tmp/racing-alpha2-demo-zybsd883`; fixture, БД, конфигурация, пароли и скриншоты
находятся вне Git. Приложение слушает только `127.0.0.1:5000`; Secure-cookie
отключена только в окружении этого локального HTTP-процесса. В репозитории и
production-настройках по умолчанию Secure-cookie включена.
