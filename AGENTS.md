# Racing Club: постоянные инструкции для разработки

## Назначение и совместимость
Racing Club — русскоязычная информационная система конного спорта: владельцы,
лошади, жокеи, соревнования и результаты. Развиваем существующее Flask-приложение.
Сохраняйте публичные страницы, поиск кириллицей, фильтры, пагинацию, CSV, календарь,
историю выступлений, статистику и `/health`. Не заменяйте backend на другой фреймворк.
Полное целевое ТЗ и границы этапов: `docs/ROADMAP_V2.md`. Не реализуйте следующий
этап без задания. Отличайте реализованные возможности от запланированных.

## Архитектура, стек, каталоги
- Python 3.14, Flask 3.1, Flask-SQLAlchemy / SQLAlchemy 2, PostgreSQL 18,
  psycopg 3; SQLite — только отдельные локальные и тестовые сценарии.
- Jinja2 + HTML/CSS/JavaScript; Gunicorn, Docker Compose; CI/CD — TeamCity.
- `app/__init__.py`: фабрика и расширения; `app/models.py`: ORM и ограничения.
- `app/auth.py`, `app/permissions.py`: аутентификация и единая политика доступа.
- `app/services.py`: спортивные операции и транзакции; `app/web.py`: представление.
- `app/application_services.py`: заявки Alpha 2, согласование и внутренние уведомления.
  Новые заявки отделены от `results`; допуск администратора относится к Alpha 3.
- `app/routes/`: blueprints; `app/templates/`, `app/static/`: интерфейс.
- `migrations/`: история Alembic; `tests/`, `verify_*.py`: проверки.
- `seed.py`: явное заполнение отдельной пустой демонстрационной БД.
- `docs/`: ТЗ, эксплуатация и подтверждённые отчёты.

## Python, Flask и SQLAlchemy
Пишите небольшие функции с явными именами, понятными ошибками и ограниченной
ответственностью. Используйте стандартную библиотеку, согласованный стиль и
закреплённые зависимости; не добавляйте сервисы без необходимости. Новые важные
контракты описывайте docstring/типами, комментариями поясняйте причины решений.
Фабрика приложения не должна менять схему или данные. Инициализируйте расширения
через `init_app`, используйте blueprints и конфигурацию приложения. Не держите
request/session в глобальных переменных, не включайте debug на публичном сервере.
Новые запросы предпочитают SQLAlchemy 2 (`select`, `session.get`, `execute`).
Проверяйте границы ID и числа, длины строк, конечность float, нормализуйте ввод.
Используйте параметры SQL, внешние ключи, уникальность и CHECK на уровне БД.
Предотвращайте N+1 в списках. Атомарные операции сохраняйте одной транзакцией;
при ошибке выполняйте rollback. Обработчики HTTP не должны показывать traceback.

## Миграции и PostgreSQL
Каждое изменение модели сопровождайте проверенной Alembic-миграцией и инструкцией
установки/обновления. Проверяйте чистую установку, обновление копии прежней схемы,
сохранение записей и соответствие metadata. Ревью автогенерации обязательно.
Исторические ревизии не импортируют текущие ORM-модели. Не используйте `create_all`
при запуске и `drop_all` для обновлений. Существующие пять спортивных таблиц и
протоколы сохраняются. SQLite не заменяет проверку PostgreSQL 18: проверяйте типы,
ограничения, транзакции, индексы, поиск и конкурентные изменения на PostgreSQL.
Миграции запускаются отдельной явной операцией, а не каждым worker Gunicorn.
Никогда не выполняйте разрушительные операции, seed или тесты на рабочих БД.
Изменения STAGE/PROD, восстановление и откаты требуют явного задания и резервной
копии; сначала репетиция в изолированной среде. Не удаляйте тома Docker.

## Доступ и безопасность
ROOT имеет все разрешения; ADMIN управляет соревнованиями, но не системными
настройками. OWNER/JOCKEY работают только с разрешёнными собственными объектами.
VIEWER — зарегистрированный зритель; GUEST — анонимный публичный просмотр.
Проверяйте централизованные разрешения и принадлежность на сервере для каждого
защищённого HTTP-метода. Скрытая кнопка не является проверкой доступа. По умолчанию
новая операция запрещена. Не принимайте из формы роль ROOT/ADMIN, статус, рейтинг,
ID чужого профиля и служебные поля. Регистрация создаёт новый профиль атомарно;
связывание прежнего профиля требует отдельной доверенной процедуры ROOT.
Пароли — только безопасные хеши; не логируйте пароли и токены. Секреты, `.env`,
дампы, БД и виртуальные окружения запрещено публиковать. Для сессий нужен постоянный
случайный SECRET_KEY, HttpOnly/SameSite, Secure под HTTPS, ограниченное время жизни,
проверка текущего статуса аккаунта. Сохраняйте CSRF на всех изменяющих запросах,
POST для выхода, ограничение попыток, безопасные перенаправления и экранирование.
Не доверяйте X-Forwarded-For без явно настроенной доверенной инфраструктуры.

## Frontend
Сохраняйте Jinja, существующую систему CSS/JS и работоспособность без JavaScript
для основных форм. Дизайн v2: чёрный/графит/белый/неоново-зелёный; публичная
горизонтальная навигация и боковое меню кабинетов — согласно дорожной карте.
Поддерживайте телефон, клавиатуру, labels, focus, сообщения ошибок, пустые состояния,
контрастность, reduced-motion и печать. Не используйте raw HTML из пользовательского
ввода. Новые библиотеки (например HTMX/Chart.js) обосновывайте; не вводите React.

## Тесты и демонстрационные данные
Изменение поведения требует содержательных позитивных и негативных проверок.
Проверяйте реальные HTTP-запросы, CSRF, обход ролей, подмену ID, отключённые аккаунты,
миграции и регрессии. Тесты должны явно создавать изолированные временные БД,
игнорировать рабочий DATABASE_URL и освобождать ресурсы. Нельзя ослаблять проверки
ради зелёного результата. Старые сценарии записи адаптируйте к авторизованной роли.
CSRF проверяйте включённым в тестах безопасности. Запускайте подходящие проверки
после исправлений и один полный итоговый набор; указывайте пропуски и ограничения.
Seed запускается только явно на отдельной пустой БД, не очищает рабочие данные,
не создаёт известных паролей. Большой связный генератор разрабатывается отдельным
этапом. Демонстрационные данные и прогнозы не содержат финансовых операций.

## GitFlow, коммиты, отчётность и проверка перед push
Основной remote — `origin` (SkRe4karta/racing-club); `legacy` (ZZAY-GIT/cyccle)
служит только исторической ссылкой, push туда запрещён. До работы проверяйте cwd,
status, ветку, remotes и актуальность базы. Работайте в отдельной feature-ветке от
актуальной dev. Не перезаписывайте чужие/незакоммиченные изменения. Запрещены прямые
изменения/push в master, dev, prod, force push, удаление веток и создание нового
репозитория. PR, merge, релиз и деплой выполняются только в разрешённом объёме.
Коммиты делайте содержательными по логическим блокам (`feat`, `fix`, `docs`, `test`),
с сообщением о назначении. Не включайте случайные файлы и локальные артефакты.
Перед push: проверьте ветку, зависимости, синтаксис, фабрику Flask, тесты, права,
CLI, миграции, сохранность данных, PostgreSQL, Docker по доступности, `git diff
--check`, весь diff и отсутствие секретов. Push — только в разрешённую ветку после
проверок. В отчёте укажите версию, ветку, SHA/ссылки, фактический результат push,
изменения схемы, функции, реальные команды и числа тестов, ограничения и следующий
этап. Никогда не объявляйте непроверенное успешно проверенным.
